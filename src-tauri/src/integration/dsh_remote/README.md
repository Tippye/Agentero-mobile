# Rust DSH Remote v1 primitives

Protocol baseline: ds-harness-remote `11064af` (0.6.4), MIT. The parent integration module enables this module with the application desktop feature (also used by mobile builds). The protocol adapter adds `snow = "0.9"`. Mobile account persistence separately uses the Rust-only keyring-store API; no generic credential plugin commands are registered in the WebView.

The available path is real REST third-party browser sign-in (OAuth provider discovery / QR-session start / poll / account profile) / account-token device registration / device-token refresh / paginated authorized Host discovery, followed by control WebSocket authorization, authenticated Noise IK and encrypted relay frames. There is no account/password login: the hosted server offers GitHub, Google and Zhihu authorization, matching dsh-Go's QR/browser flow. `RpcClient` owns the channel in a Tokio task and correlates concurrent requests. It supports DSH secure fragmentation, events, capability probing, and the official `harness.remote.call` result envelope. Only control-socket relay is advertised; independent relay attach, LAN, P2P, TURN, browser authentication and device pairing are not advertised.

## Rust integration

1. Construct `ServerApi` with an HTTPS origin (or a literal loopback/private HTTP origin). Redirects are disabled. REST responses and deadlines are bounded.
2. Generate or restore `DeviceIdentity`. Persist its private key only through the platform credential store. Authenticate using `oauth_providers` → `start_oauth_qr` → `poll_oauth_qr` (the user authorizes in a browser; the account token is delivered exactly once) → `account_me`, then `register`. Discovery entry paths must stay same-origin under `/api/v1/auth/`, and the scan URL must stay on the server origin. `register` also accepts an existing same-server account bearer token. Persist token pairs atomically, including a successful `refresh`, before using them. Errors do not clear existing credentials or trigger retries.
3. Fetch `ServerApi::host`. Show its identity to the user and persist an approved pin in the platform trust store. Initial approval trusts the server-supplied identity. Pass the stored pin to `RelayChannel::connect`; every connection re-fetches the authorized descriptor and refuses changed keys before opening the WebSocket.
4. Start one `RpcClient` per client-device/Host pair and call `describe`. Old ApiProxy-only Hosts are refused. Select the official Harness Session wire format from the negotiated `harness.remote.v1` or `harness.remote.v3` capability. The relay layer does not invent or translate session data.
5. Mutations use `call_with_id` or `harness_call` with `CallSemantics::Mutation` and a stable application operation ID. Treat `outcome_unknown` as potentially executed. There are no automatic reconnects, retries, mutation replays, or fallback calls. All dispatched request IDs remain reserved for that channel, including timed-out reads, so a late response cannot complete another call with a reused ID. The bounded ID ledger requires a fresh connection after 16,384 requests. The application service must retain operation receipts across connection replacement; a new Noise channel does not establish that an old operation failed.
6. Event receivers must treat broadcast lag as a resync requirement and use official snapshot/history/stream APIs. Select `wait_closed` alongside event reception to observe channel closure. `close` disconnects every clone of the shared client and resolves pending RPCs conservatively. Provider disconnect closes the Host clients even if another window retains a clone.

`DshRemoteProvider` implements account connection, resume and discovery, then native Harness workspaces, root sessions, complete text history, subscriptions, create, queued prompts, cancellation requests, connection-owned one-time approvals, blocking/timed/continued structured questions, workspace upload, and launch-memory operation receipts. Native operations are advertised only after a pinned Host negotiates exactly one `harness.remote.v1|v3` carrier and its official `$events` owner is ready. Upload additionally requires `workspace.upload.v1`; relay upload is capped at 20 MiB and the Host may enforce a smaller limit. ACP and Codex remain unsupported. No old `harness.api.*` or `sync.from` fallback is used.

The pinned Server permits one active control socket and Host link per client identity. Initial `connect` selects the first sorted online approved Host; `select_host(&HostRef)` explicitly switches, closing the previous channel and its interaction claims. Then call the shared service's `resume` to refresh its cached capabilities. Resume preserves the selected active Host. Ordinary calls to another Host return `CONNECTION_IN_USE`, so one window cannot silently replace another window's active session. Disconnect before replacing configuration, credentials or trust pins through `configure`; receipts survive disconnect/reconfiguration within this provider instance.

Workspace membership comes from `workspace/follow` session IDs, never a caller's cwd. Subagent sessions are filtered from the root catalog. `session/follow` provides an authoritative snapshot and cursor; older `session/page` results are fetched until history is complete, bounded to 32 MiB / 100,000 records and a 120-second total budget. Oversize/incomplete recovery fails explicitly. Native user/assistant final text messages and turn state map to the shared contract with native seq IDs and namespaced cursors. Tool/chunk/image/replacement surfaces lack faithful equivalents in that contract and are omitted; final text messages remain available. Live follow uses the durable event stream (no `assistantStream:true` request), and read→subscribe recovers via a fresh official snapshot plus cursor-filtered pagination.

`CreateSession` with a requested title is unsupported because upstream `session/create` has no title argument; creation is not silently followed by another mutation. Uploaded file references are appended as explicit workspace paths in prompt text, matching the tablet context design. The trusted Rust file-picker owner must first grant an already-open regular file through `grant_upload_file`; an IPC path string alone provides no filesystem authority. Grants are consumed once and file size/time are rechecked before upload. Upload publication success validates the Host's returned relative path and byte count; lost commit replies remain Unknown and are never replayed.

Approvals use the owning `$events.ready.clientId`, event ID and native session ID; only `allowed-once` / `rejected` are accepted. Blocking questions use the same event result carrier. Timed questions open `userQuestions/attachWait` and only permit answers within its deadline; expiry returns `ASK_TIMED_OUT` once. Continued questions recovered from authoritative `userQuestions` projections use `userQuestions/answer` and true means queued/accepted, never completed work. Answers consume their local handles before dispatch; disconnect never replays answers. Operation receipts are bounded, launch-memory observations; missing receipts never authorize resending.

## Verification

`cargo test -p agentero --lib integration::dsh_remote` exercises the unchanged upstream Noise handshake / transport ciphertext / nonce vector, upstream envelope and relay fixtures, strict JSON and URL parsing, tampering/replay/binding rejection, secure fragment limits and sequence validation, REST pagination, the third-party sign-in flow (provider discovery with the legacy 404 fallback, QR-session start/poll, account profile and device registration, cross-origin scan-URL and unsafe entry-path rejection), and an actual loopback REST → WebSocket → Noise → encrypted RPC test. That integration test drops a mutation response, rejects duplicate replay, discards a late response, receives an event and reassembles a 100 KB RPC result. It also checks nonce-bearing control heartbeats. Native mocked-wire fixtures additionally assert exact catalog/history/create/prompt/cancel/approval/question/upload payloads, owner binding, root-session membership, read/subscription cursor recovery, claim expiry, dedicated upload framing and unknown mutation behavior. The native fixture is a source-grounded test vector assembled from the pinned upstream client and its tests, not an upstream published fixture. No real account or external Host is needed.

Cryptographic operations use snow's fixed `Noise_IK_25519_ChaChaPoly_SHA256` implementation. Deterministic ephemeral keys are used only by the golden-vector test. Production handshakes use snow's cryptographic random source. See THIRD_PARTY_LICENSES.md for upstream attribution.
